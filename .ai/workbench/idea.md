# Idea

- Workflow to follow when working with local AI models of small size (7B to 35B), with limited context window size (32k to 64k).
- Persisting knowledge in markdown files, so new sessions can read them and use its knowledge to perform the task:
  - The files should not be so long, to avoid filling the context fast.
  - The files should be succint, concise and small, containing only the information the agent needs.
  - If there is the need to long files, then the information should be broken down into pieces semantically aligned and linked together using markdown links syntax (`[link name](path)`).
- Plan before Act principle:
  - The agent should plan the task, dump the planning into a markdown file, then (preferably in a new session), implement it.
  - The user should iterate on the task plan before asking the agent to implement it.
  - The idea is to avoid hallucinations and prevent the agent to implement the wrong thing.
- The workflow should be modular.
- Full workflow based on Spec Driven Development:
  - Constitution of the project (optional):
    - A mission file, containing the mission and vision of the project.
    - A techstack file, containing information about the stack of the project (language, framework, testing framework, db, etc.)
  - Phases (optional):
    - The phases are the high abstract steps that forms the project:
      - It can be steps from a roadmap, like:
        - Project bootstrap.
        - Auth module implementation.
        - ...
      - It can be interpreted as a feature.
      - Or it can be interpreted as a semantical grouping of tasks.
    - The phases should contain:
      - The context for that phase (a small section that contains information needed for that phase, like a previous research).
      - The scope of the phase, and what is not in scope.
      - The requirements of the phase, what it should produce to be considered as done.
      - The validations step, what should be done to confirm that the requirements are met.
      - A sequence of steps (tasks descriptions) that should be made to complete this phase.
    - The phases are not immutable, a new task can be added, it can be replanned if any deviation appear, it can have its scope extended, or pruned.
  - Tasks (required):
    - This are the files that defines the workflow.
    - A task is a unit of work.
    - It is similar as phase files, but it is way more detailed.
    - It should contain:
      - The context for that task, like a small research that is needed to implement that task.
      - The files it will create or modify.
      - What is on scope and not on scope.
      - Requirements.
      - Validations.
      - Step by step of what will be done:
        - Example:
          - Create file.
          - Create function.
          - Add code to function.
        - This is the part that will guide the implementation.
        - It can contain pseudocode to guide the implementation as well.
        - It should not contain real code, this will be generated later.
- This workflow has to be explained in a file that is read for every section. This file should be linked inside the AGENTS.md file of the user.
- The files of this workflow should not be forced upon for commit, only if the user wants it:
  - If the user wants to commit this files, then the files should be commited for every draft created or any changes made on the drafts.
